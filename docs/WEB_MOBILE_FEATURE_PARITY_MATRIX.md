# Web ↔ Mobile Feature Parity Matrix (Phase 2)

Read-only audit. Produced from direct source reading in both repositories
(Django `Career_Buddy_LMS/` as reference, Flutter `Mobile_app/` as the
port) plus five focused research passes, one per feature area, each citing
exact file:line evidence on both sides. No source file was modified to
produce this matrix. `android/key.properties` was never read. No network
request, server start, or test run was needed to produce this document
(a handful of entries note that a specific sub-finding would benefit from
on-device confirmation — those are marked **Uncertain**, not assumed).

**Status definitions** (per the task's required wording):
- **Fully equivalent** — source evidence supports equivalent functionality
  and business behavior; this does **not** imply the behavior was run and
  observed, only that it was read and traced.
- **Partial** — some functionality exists but a specific capability,
  validation, state, or transition is missing or weaker.
- **Missing** — web supports a capability with no mobile counterpart at all.
- **Intentionally different** — a documented or defensible mobile-specific
  difference that preserves the core capability.
- **Blocked** — depends on a real external prerequisite unavailable to
  this engagement (backend deployment, account tier, device, credentials).
- **Uncertain** — evidence is insufficient to classify with confidence;
  typically flagged for a device check.

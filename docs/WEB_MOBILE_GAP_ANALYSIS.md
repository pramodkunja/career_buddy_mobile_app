## 4. Root-cause findings: bot navigation & related questions

**Bot navigation — no contract mismatch, no action needed.** Every field Flutter reads for navigation (`reply`, `actions[].key/label/route`, `source`) is read under its real name from the real `/api/riya/chat/stream/` response; the auto-navigate trigger condition (`source ∈ {intent, skillup} && actions.length === 1`) is a byte-for-byte port of `BOTscript.js`'s own check; every literal route the server can return today has a mapped case in `ariaActionFlutterRoute` (only the web's own `about_app` no-op route, `route: ""`, is unmapped, matching the web's own behavior). The one structural asymmetry found: `BOTscript.js` has an explicit 15-second stall-timeout watchdog that force-navigates if TTS playback never starts; `AriaChatController` has no equivalent — if audio playback ever hung without completing, Flutter's pending navigation would never fire. No evidence this has actually happened (`aria_voice_playback_service_impl.dart` was not found to hang in practice); this is a low-priority robustness note, not a confirmed bug.

**Related/follow-up questions — root cause of the apparent "gap" is web-side code health, not a Flutter defect.** Flutter's post-reply chip rendering was initially suspicious (it does something the main web widget's code explicitly stubs out), but tracing further shows: (1) the server-side `actions` field Flutter renders is genuinely real and already used for bot-navigation chips elsewhere, so Flutter isn't inventing data; (2) a second, separate web widget (`riya-embed.js`) does render these same chips, confirming the mechanism is intentional product behavior somewhere in this system, just not wired into the widget most users see. The actionable root cause to flag to the web team: either `BOTscript.js`'s `setActionChips` no-op is an unfinished migration (in which case the main web widget is the one with the gap, not Flutter), or it's a deliberate deprecation in favor of the persistent `WELCOME_CONTEXT`/`SECTION_CONTEXT` panel (in which case Flutter rendering post-reply chips at all should be a product decision, not assumed). No comment in either web file states which. **Recommendation: do not change Flutter's chip-rendering behavior in Phase 5 until this is confirmed with whoever owns the web chat widget** (see §9).

## 5. Required subscription behavior and restrictions

Documented from code, not invented:
- Three plans: `free`, `normal` (₹499 + 18% GST = ₹588.82/yr, `career_app/views.py:219-223`), `pro` (₹999 + 18% GST = ₹1178.82/yr). Feature differences per `templates/pro.html` (Free: no AI Mock Interview; Normal: AI Mock Interview + a capped job-recommendation count of 5, `JOB_RECOMMENDATION_LIMITS`, `views.py:135`; Pro: uncapped).
- Plan status is server-computed and self-healing (`users/models.py:123-197`): active until `subscription_start + 365 days`; an expired paid plan auto-reverts to Free and sets a one-time `pending_expiry_notice` flag the UI should surface.
- Manual downgrade to Free is blocked server-side while a paid term is still active (`can_downgrade_to_free`, `users/models.py:199-203`; enforced again in `toggle_pro_status`, `career_app/views.py:195`).
- Checkout is a real Razorpay integration with genuine anti-tampering: the order is created with **server-set** notes (`user_id`, `plan`, `amount_paise` — never trusts a client-supplied plan/amount), and verification re-fetches the order from Razorpay itself and checks its server-set notes/amount/status before activating anything (`career_app/views.py:525-708`, see the inline "PAY-01 fix" comment at 556-561 describing exactly the privilege-escalation attack this defeats). A second, independent webhook path (`views.py:1604-1779+`) provides idempotent, signature-verified activation and refund handling. **This is a mature, already-hardened payment flow** — any mobile implementation must reuse it (via its existing `JsonResponse`-returning endpoints) rather than re-implement verification logic client-side or trust a client-reported "payment succeeded" state.
- A Flutter subscription screen would need, at minimum: a way to read current plan/expiry (no JSON endpoint exists for this today — `pro_page` only renders HTML; this is a real backend gap, not something to build in this phase per the "no new APIs" rule, but worth flagging to the backend owner given they're already actively adding JSON siblings for other views, per §1), the existing `create_razorpay_order`/`verify_razorpay_payment` JSON endpoints, and either the Razorpay Flutter SDK or an embedded webview to actually run their checkout UI (neither exists in the Flutter project today).

## 6. Recommended implementation phases

Findings justify a different emphasis than the originally suggested order: bot navigation and predefined/related questions (originally Phases 4–5) are **already correctly implemented with no material gap**, so they shift from "build" phases to a single short verification/decision step. The real remaining build effort concentrates in Home entry-routing (small) and Subscription (large). Revised order:

1. **Phase 2 — Home entry-point routing fix** (small, no dependencies). Make a logged-out cold launch land on `/home` (or redirect `splash` there for `AuthUnauthenticated`) instead of `/login`, matching the real web's "home page is where role selection happens" behavior.
2. **Phase 3 — Subscription screen and subscription-aware navigation** (large; depends on nothing from Phase 2, but should land before Phase 4 since bot navigation already produces real `/pro/`-routed actions that currently hit a placeholder). Builds a real plan-status display, wires the existing Razorpay JSON endpoints, and replaces the `RoutePaths.pro` placeholder.
3. **Phase 4 — Bot navigation & related-questions verification** (small; re-scoped from a build phase to a confirmation phase). No code changes expected unless the web-widget ambiguity in §4 is resolved in a way that implies a Flutter change (e.g. if product confirms post-reply chips should NOT appear, or confirms the stall-timeout watchdog gap should be closed).
4. **Phase 5 — (merged into Phase 4 above)**: originally "predefined and related questions" — folded in since the investigation is the same effort and the same open question (§9) governs both.
5. **Phase 6 — Cross-feature regression testing and end-to-end verification** (unchanged from the suggested order) — now covering Phases 2 and 3's new code plus a regression pass confirming Phase 4's conclusions didn't require changes.
